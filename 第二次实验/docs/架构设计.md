## 1 设计目标与约束

### 1.1 需求基线

| 对象 | 状态数 | 关键约束 |
| --- | --- | --- |
| 商品 | 8 | 只允许 REQ-029 列出的转换，已完成不可再变 |
| 预约 | 5 | 同一商品任一时点只允许一条有效预约（REQ-008） |
| 订单 | 5 | 由预约生成，终态不可逆（REQ-024） |

三条主线：**商品上架审核**、**预约交易**、**信用风控**。

### 1.2 非功能约束及其设计影响

| 需求 | 约束 | 对设计的影响 |
| --- | --- | --- |
| REQ-020 | 单机 4C/8G、MySQL 8.0 单实例、应用单实例、不用集群与缓存中间件 | 单体分模块，不引 Redis/MQ；超时用进程内定时任务；通知用站内消息表 |
| REQ-022 | 1 万条已发布商品、20 并发、95% 查询 1 秒内 | 检索独立成模块，只读、走组合索引；写路径不持有读路径要用的锁 |
| REQ-019 | 密码哈希、越权拒绝、连续失败 5 次锁定 30 分钟 | 认证鉴权集中在接入层；锁定状态独立表 |
| REQ-027 | 关键操作留痕、可查、不可改、失败不留成功记录 | 审计与业务同事务写入，不用 AOP 事后补记 |
| REQ-028 | 逻辑删除；删商品级联作废预约与订单 | 软删除字段 + 同事务同步事件级联，不用数据库级联 |

### 1.3 设计原则

1. **按业务能力划分模块，一个聚合根只有一个写入方。** 商品、预约、订单、违约、举报、操作记录分别只由一个模块写。
2. **状态转换集中且可枚举。** REQ-029 要求逐条验收，转换规则必须是一张能对着需求表核对的表，而不是散落在各处的 if。
3. **事务边界显式化。** 卖家确认、下单、完成、下架级联、审核驳回都必须在同一事务内完成。
4. **跨模块只走接口与事件，不跨模块访问数据表。** 反向联动（商品下架要作废订单）用同事务同步事件解除循环依赖。
5. **能留 TODO 的地方留 TODO。** 支付、物流、CDN 按 REQ-023 不做。

## 2 总体架构

### 2.1 架构风格

**模块化单体（modular monolith）+ 前后端分离**：

- 后端一个 Spring Boot 进程，内部按业务域分包；模块之间只能通过 `xxxApi` 接口、领域事件和公共层端口交互，禁止 import 对方 Mapper、禁止跨模块写表。
- 前端三个入口：买家 H5、卖家 H5（同一移动端工程，按角色渲染菜单）、管理员后台（PC）。
- 前后端只走 REST，统一 `/api/v1/**`，统一返回 `{code, message, data}`。

不选微服务：REQ-020 把环境钉死在单机单实例、不允许缓存与消息中间件，注册中心、网关、分布式事务全部超出环境；课程周期也没有运维投入。模块边界按域划好，后续要拆服务时按包平移。

### 2.2 运行时结构

```
浏览器 / 手机浏览器
   │ HTTPS + JSON
   ▼
Spring Boot 应用（单实例）
   ├─ 接入层：会话校验、角色鉴权、封禁拦截、参数校验、统一异常
   ├─ 应用服务：用例编排、事务边界（@Transactional）
   ├─ 领域层：实体、状态转换表、守卫、可见性规则、违约累计
   ├─ 仓储层：MyBatis-Plus Mapper
   └─ 定时任务：每 30 秒分批扫到期预约/订单（单实例不会重复执行）
   │ JDBC
   ▼
MySQL 8.0（单实例）
```

### 2.3 技术栈

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 后端 | Spring Boot 3.3（JDK 17 目标版本） | 与课程 Java 背景一致 |
| 持久层 | MyBatis-Plus 3.5 + MySQL 8.0 | 唯一索引冲突、统计聚合手写 SQL |
| 认证 | Spring Security + HttpSession | 单实例不需要 JWT/Redis；锁定表存失败计数 |
| 移动端 | Vue 3 + Vite + Vant 4 + Pinia | 买家/卖家共用工程 |
| 管理后台 | Vue 3 + Vite + Element Plus | 审核、举报、封禁、统计、审计 |
| 构建 | Gradle / pnpm | 本机已有 JDK、Node、MySQL 8 |
| 部署 | Nginx 静态资源 + jar + MySQL | 单机 |

## 3 模块划分

### 3.1 划分依据

1. **按聚合根划分**：用户、商品、预约、订单、违约记录、举报、操作记录、通知，各自只有一个写入方。
2. **按读写特征划分**：检索是纯读路径（REQ-022 的性能靶子），与商品写路径分开，避免写事务拖慢查询。
3. **按触发来源划分**：违约记录被 4 个地方触发（审核驳回、卖家超时、买家取消、举报成立），集中到一个模块才能保证“6 个月 5 次”的口径一致。
4. **按事务边界划分**：同一事务要一起成功/失败的动作放在同一个应用服务里，跨模块联动用同步事件。

### 3.2 模块清单（7 个业务模块 + 1 个公共层）

| --- | --- | --- | --- | --- |
| M1 | 账号与权限 | 注册、登录、BCrypt 哈希、失败计数与锁定、会话、角色鉴权、封禁状态判定 | `t_user`、`t_login_attempt` | REQ-001、REQ-002、REQ-019、REQ-018（拦截） |

### 3.4 模块依赖

编译期依赖只允许下表方向，且必须无环：

| 模块 | 依赖 | 依赖方式 |
| --- | --- | --- |
| M1 | M0 | — |
| M2 | M0、M1、M5、M6 | 调 `CreditPort.record()`、`NotifyPort.send()` |
| M3 | M0、M2 | 只读调用 `ProductQueryApi` |
| M4 | M0、M1、M2、M5、M6 | 查商品状态、记违约、发通知 |
| M5 | M0、M1、M6 | 封禁与举报结果通知 |
| M6 | M0、M1 | 收件人校验 |
| M7 | M0 | 实现 `AuditPort`；统计读只读视图 |

两条关键规则：

1. **商品下架要作废预约与订单，但不能让 M2 依赖 M4**（否则 M4 查商品状态就成环）。做法：M2 在事务内发布 `ProductOfflineEvent`，M4 用 `@EventListener` 同步消费，在同一事务里作废预约与订单；事务回滚则事件处理一起回滚。
2. **审计不让业务模块依赖 M7**。`AuditPort` 接口定义在 M0，M7 实现；业务模块只依赖 M0，调用时把操作人、前后状态传进去，与业务同事务落库。

依赖图为有向无环图：

```
M1 ← M2 ← M3
     ↑    ↑
     M4 ──┘
     ↑
M5 ──┘（M5 只被 M2、M4 调用）
M6 ← M2、M4、M5
M0 ← 全部
M7 ← 通过 M0 的 AuditPort 被调用，统计只读库
```

## 4 模块间交互

### 4.1 交互方式

| 方式 | 场景 | 一致性 |
| --- | --- | --- |
| 应用服务同步调用 | 校验、状态转换、记违约 | 同事务，失败一起回滚 |
| 同事务同步事件 | 商品下架→作废预约与订单；商品删除→级联 | 同事务，原子 |
| 事务提交后事件 | 通知推送（未读数刷新、SSE） | 提交后才推，回滚不推 |
| 定时任务 | 预约 24h 未确认、订单 24h 未下单 | 分批 + 幂等更新 |
| 只读查询 | 商品列表、统计、操作记录 | 不加锁 |

### 4.2 三条关键交互链

**（1）预约链**：买家 → M4 预约接口 → `ProductQueryApi` 校验商品为“已发布” → 插入预约（`active_key` 唯一索引兜底）→ 商品转“已预约” → 写审计 → 通知落库 → 提交后推送。并发时第二个请求在唯一索引上直接失败，不需要先查后插。

**（2）审核链**：卖家提交 → M2 状态转“待审核” → 管理员审核 → 通过则“已发布”；驳回则“已驳回”，同事务调 M5 记卖家违约一次，再判断是否满 5 次触发封禁。

**（3）超时链**：定时任务按 `(state, confirm_deadline)` 索引取 200 条 → 逐条 `UPDATE ... WHERE id=? AND state='待卖家确认'` 幂等置“已失效” → 商品回“已发布” → M5 记卖家违约 → 审计 → 通知买家与管理员（提交后推送）。

### 4.3 事务边界

| 操作 | 同一事务内必须完成 |
| --- | --- |
| 卖家确认预约 | 预约→已确认、商品→交易中、其余预约→已作废、订单→待下单、审计、通知落库 |
| 买家下单 | 订单→已下单、审计、通知 |
| 交易完成 | 订单→已完成、商品→已完成、审计、通知 |
| 下架商品 | 商品→已下架、`ProductOfflineEvent` → 预约作废、订单作废、审计、通知 |
| 审核驳回 | 商品→已驳回、违约 +1、封禁判定、审计、通知 |
| 举报核实成立 | 举报→成立、违约 +1、封禁判定、审计、通知 |

## 5 关键设计决策

| 编号 | 决策点 | v2 方案 | 否掉的方案与原因 |
| --- | --- | --- | --- |
| ADR-01 | 模块划分 | 7 个业务模块：检索独立、信用独立、通知独立 | 5 个模块（v1）：检索混在商品里性能优化不好单独做；违约分散在商品与交易两个模块，口径会漂 |
| ADR-02 | 商品状态机 | 状态转换表（15 条规则）+ 守卫链，非法转换统一抛 `IllegalStateTransition` | 状态模式（v1）：8 个类各写一套方法，20 条转换散在 8 个类里，REQ-029 要逐条验收时对不上表；枚举 + if：规则与权限混在一起 |
| ADR-03 | 唯一有效预约 | `active_key` 生成列（有效状态时=商品 ID，终态为 NULL）+ 唯一索引，插入冲突即拒绝 | 行锁（v1）：锁商品行会挡住同商品详情查询，和 REQ-022 的并发查询目标冲突；乐观锁：预约是插入不是更新，重试易双重插入 |
| ADR-04 | 超时处理 | `(state, deadline)` 索引 + 每批 200 条 + 幂等 UPDATE | 全表扫描（v1）：`deadline < now()` 无索引；MySQL EVENT：业务逻辑落进数据库，难调试难单测 |
| ADR-05 | 通知 | 通知与业务同事务落库；`@TransactionalEventListener(AFTER_COMMIT)` 只负责推送 | v1 在业务方法里同步写通知（回滚后仍留消息）；只靠 AFTER_COMMIT 落库则进程崩溃会丢消息 |
| ADR-06 | 跨模块级联 | 同事务同步事件（`ProductOfflineEvent`） | 直接调用 M4（形成 M2↔M4 循环依赖） |
| ADR-07 | 联系方式可见性 | 实时推导：查询时看是否存在有效预约/未结束订单 | 可见性表（v1）：每次状态变化都要同步，漏一处就泄露或误藏；定时清理有回收时间差 |
| ADR-08 | 操作记录 | 显式调用 `AuditPort`，与业务同事务写入 | AOP 切面（v1）：切面拿不到业务的前后状态，操作失败时也可能留下记录，违反 REQ-027 |
| ADR-09 | 逻辑删除 | 各表 `deleted` + 仓储统一拼接条件；删除商品触发级联 | v1 保留；补充“已完成订单不可删除”在服务层硬校验 |
| ADR-10 | 鉴权 | HttpSession + 拦截器 + 注解 `@RequireRole`；封禁在写操作前拦截 | v1 保留；补充封禁拦截点集中到拦截器，避免各接口各写一遍 |

### 5.1 状态转换表（商品，15 条）

| # | 从 | 动作 | 到 | 守卫 |
| --- | --- | --- | --- | --- |
| 1 | 草稿 | 提交审核 | 待审核 | 卖家本人、未封禁 |
| 2 | 待审核 | 审核通过 | 已发布 | 管理员 |
| 3 | 待审核 | 审核驳回 | 已驳回 | 管理员、必须填理由 |
| 4 | 已驳回 | 修改后重新提交 | 待审核 | 卖家本人、未封禁 |
| 5 | 已发布 | 买家预约 | 已预约 | 买家、非本人商品、未封禁 |
| 6 | 已预约 | 卖家确认 | 交易中 | 卖家本人、24 小时内 |
| 7 | 交易中 | 线下交付完成 | 已完成 | 交易双方之一 |
| 8 | 已发布 | 卖家下架 | 已下架 | 卖家本人 |
| 9 | 已预约 | 卖家下架 | 已下架 | 卖家本人 |
| 10 | 已发布 | 管理员下架 | 已下架 | 管理员、须有违规依据 |
| 11 | 已预约 | 管理员下架 | 已下架 | 管理员、须有违规依据 |
| 12 | 交易中 | 管理员下架 | 已下架 | 管理员、须有违规依据 |
| 13 | 已预约 | 预约取消/超时 | 已发布 | 系统 |
| 14 | 交易中 | 订单取消/超时 | 已发布 | 系统 |
| 15 | 已下架 | 重新提交审核 | 待审核 | 卖家本人、未封禁 |

禁止的转换由同一张表兜底：不在表里的（from, action）一律拒绝，例如“待审核→已预约”“已预约→已完成”“已完成→任意”。

### 5.2 守卫链

`StateGuard`（当前状态必须是规则里的 from）→ `RoleGuard`（操作人角色）→ `OwnerGuard`（卖家只能动自己的商品）→ `BanGuard`（被封禁不得上架/改价/预约/下单）→ `ReasonGuard`（管理员下架/删除必须填依据）。任一守卫失败即抛业务异常，状态不变。

## 6 数据存储设计

### 6.1 表清单

### 6.2 关键约束

```sql
-- 同一商品只允许一条有效预约：终态时 active_key 为 NULL，NULL 不参与唯一性
ALTER TABLE t_reservation
  ADD COLUMN active_key BIGINT GENERATED ALWAYS AS (
    CASE WHEN state IN ('WAIT_SELLER','CONFIRMED') THEN product_id END
  ) STORED,
  ADD UNIQUE KEY uk_reservation_active (active_key);

-- 超时扫描走索引
CREATE INDEX idx_reservation_deadline ON t_reservation (state, confirm_deadline);
CREATE INDEX idx_order_deadline       ON t_order       (state, place_deadline);

-- 检索（REQ-022）
CREATE INDEX idx_product_search ON t_product (state, category_tag, price);

-- 统计与审计查询
CREATE INDEX idx_violation_user_time ON t_violation (user_id, occurred_at);
CREATE INDEX idx_oplog_target        ON t_operation_log (target_type, target_id);
CREATE INDEX idx_oplog_operator      ON t_operation_log (operator_id, created_at);
```

### 6.3 存储与保留

- 商品、预约、订单一律逻辑删除，`deleted=0` 由仓储统一拼接；已完成订单不可删除（服务层校验）。
- 操作记录、举报保存 1 年；交易记录与账号信息长期保留（REQ-017、REQ-027）。
- 商品图片存本地目录，DB 存相对路径（不接第三方对象存储，REQ-023）。

## 7 部署设计

```
[买家/卖家手机浏览器] --HTTPS--> [Nginx :443]
                                     ├─ /            → 前端 dist（H5）
                                     └─ /api/**      → [Spring Boot :8080] --JDBC--> [MySQL 8.0 :3306]
[管理员 PC 浏览器]    --HTTPS-->      └─ /admin/**    → 前端 dist（后台）        └─ 本地磁盘：图片目录
```

- 应用单实例，`-Xmx2g`；定时任务与应用同进程，单实例不会重复执行。
- 不部署集群、不用 Redis/MQ、不接 CDN，与 REQ-020 的约定环境一致。
- 备份：MySQL 每日全量 dump 到本地磁盘（原型阶段手工执行，列入 TODO）。
