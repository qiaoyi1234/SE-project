## 1 设计目标与约束

### 1.1 需求基线

实验一共确认 26 条需求（功能 21、非功能 4、约束 1），核心业务对象与状态数量如下：

| 对象 | 状态数 | 关键约束 |
| --- | --- | --- |
| 商品 | 8 | 状态转换只允许 REQ-029 列出的 20 条，已完成不可再变 |
| 预约 | 5 | 同一商品任一时点只允许一条有效预约（REQ-008） |
| 订单 | 5 | 由预约生成，终态不可逆（REQ-024） |

三条主线贯穿设计：**商品上架审核**（草稿→审核→发布→下架）、**预约交易**（发布→预约→确认→下单→交付）、**信用风控**（违约累计→封禁→举报）。

### 1.2 非功能约束对架构的直接影响

| 需求 | 约束 | 对设计的影响 |
| --- | --- | --- |
| REQ-020 | 单机 4C/8G、MySQL 8.0 单实例、应用单实例、不用集群与缓存中间件 | 不做微服务、不引入 Redis/MQ；超时用进程内定时任务，通知用站内消息表 |
| REQ-022 | 1 万条已发布商品、20 并发、95% 查询 1 秒内 | 查询走独立只读路径与组合索引，不与写事务抢锁 |
| REQ-019 | 密码哈希、越权拒绝、连续失败 5 次锁定 30 分钟 | 认证与鉴权集中在接入层统一拦截，业务代码不各自校验 |
| REQ-027 | 关键操作留痕、可查、不可改、失败不留成功记录 | 操作记录与业务变更在同一事务内写入 |
| REQ-028 | 一律逻辑删除；删商品要级联作废预约与订单 | 软删除字段 + 应用层级联，不用数据库物理外键级联 |

### 1.3 设计原则

1. **按业务能力划分模块，不按页面划分。** 一个模块对应一个聚合根和一组需求，保证每个状态机只有一个归属模块。
2. **状态转换集中校验。** REQ-029 要求逐条验收允许/禁止的转换，转换规则必须可枚举、可单测，不能散落在各个接口里。
3. **事务边界显式化。** 订单与商品同事务、下架级联同事务、操作记录同事务。
4. **能留 TODO 的地方留 TODO。** 本期只保证原型结构完整，支付、物流、图片 CDN 等按 REQ-023 不做。

## 2 总体架构

### 2.1 架构风格

采用**模块化单体（modular monolith）+ 前后端分离**：

- 后端一个 Spring Boot 进程，内部按业务域分包，模块之间只能通过应用服务接口调用，禁止跨模块直接访问对方数据表。
- 前端拆成三个入口：买家 H5、卖家 H5（同一套移动端工程，按角色切换菜单）、管理员后台（PC）。
- 前后端只通过 REST 接口交互，接口统一 `/api/v1/**`，返回统一结构 `{code, message, data}`。

不选微服务的原因：REQ-020 把部署环境钉死在单机单实例、不允许缓存与消息中间件，微服务带来的注册中心、网关、分布式事务全部超出这个环境；课程周期内也没有运维投入。模块化单体保留了按域拆分的边界，后续要拆服务时按包边界平移即可。

### 2.2 运行时结构

```
浏览器 / 手机浏览器
   │ HTTPS + JSON
   ▼
Spring Boot 应用（单实例）
   ├─ 接入层：登录拦截、角色鉴权、参数校验、统一异常处理
   ├─ 应用服务层：用例编排（预约、确认、下单、审核……），事务边界
   ├─ 领域层：实体、状态机、领域规则（唯一有效预约、联系方式可见性、违约累计）
   ├─ 仓储层：MyBatis-Plus Mapper
   └─ 定时任务线程：超时扫描（预约 24h 未确认、订单 24h 未下单）
   │ JDBC
   ▼
MySQL 8.0（单实例）
```

### 2.3 技术栈

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 后端框架 | Spring Boot 3.3（JDK 17 目标版本） | 与课程 Java 背景一致 |
| 持久层 | MyBatis-Plus 3.5 + MySQL 8.0 | 需要手写部分 SQL（唯一索引冲突、统计聚合） |
| 认证 | Spring Security + 会话（HttpSession） | 单实例部署，不引入 JWT 与 Redis；锁定状态存会话表 |
| 前端（移动端） | Vue 3 + Vite + Vant 4 + Pinia | 买家/卖家共用一个工程，按角色渲染 |
| 前端（管理后台） | Vue 3 + Vite + Element Plus | 审核、举报、封禁、统计、审计 |
| 构建 | Gradle（后端）/ pnpm（前端） | 本机已具备 JDK、Node、MySQL |
| 部署 | Nginx 静态资源 + Spring Boot jar + MySQL | 单机 |

## 3 模块划分

### 3.1 划分依据

1. **按聚合根划分**：用户、商品、预约、订单、违约记录、举报、操作记录，各自只由一个模块负责写。
2. **按变化频率划分**：商品主数据变化慢，交易过程数据变化快，检索是纯读路径，三者分开后互不影响。
3. **按事务边界划分**：需要在同一事务内完成的动作放在同一个应用服务里；跨模块的联动通过应用服务编排，不通过数据库触发器。

### 3.2 模块清单（v1：5 个业务模块 + 1 个公共层）

| 编号 | 模块 | 职责 | 关键需求 |
| --- | --- | --- | --- |
| M1 | 用户与权限模块 | 注册、登录、密码哈希、失败锁定、角色鉴权、封禁状态拦截 | REQ-001、REQ-002、REQ-019、REQ-018（封禁校验部分） |
| M2 | 商品模块 | 商品创建与编辑、分类标签、价格调整、提交审核、管理员审核、上下架、逻辑删除、多条件查询与分页 | REQ-003、REQ-004、REQ-005、REQ-006、REQ-028、REQ-029 |
| M3 | 交易模块 | 预约、唯一有效预约、卖家确认、下单、取消预约、取消下单、交易完成、超时处理、联系方式可见性 | REQ-008、REQ-009、REQ-010、REQ-011、REQ-012、REQ-024、REQ-025、REQ-026 |
| M4 | 管理模块 | 举报受理与核实、违约记录、累计封禁、解封审批 | REQ-013、REQ-018 |
| M5 | 审计与统计模块 | 操作记录写入与查询、三类统计、数据保留 | REQ-016、REQ-017、REQ-027 |
| M0 | 公共层 | 统一返回、异常、鉴权拦截、事务模板、定时任务调度、日志 | 全模块 |

### 3.4 模块依赖

依赖方向固定为「上层→下层、业务→公共」，禁止反向依赖与循环依赖：

```
M1 用户与权限  ←  所有业务模块（都要鉴权、都要判断封禁）
M2 商品        ←  M3 交易
M3 交易        ←  （无）
M4 管理        →  M2、M3（审核、下架、作废）
M5 审计与统计  ←  所有业务模块（写操作记录）
M0 公共层      ←  所有模块
```

| 状态变化后的联系方式权限、举报、操作记录 | M3（联系方式）、M4（举报）、M5（操作记录） |

## 4 模块间交互

### 4.1 交互方式

| 方式 | 使用场景 | 说明 |
| --- | --- | --- |
| 应用服务同步调用 | 校验、状态转换、级联作废 | 同一事务内，失败一起回滚 |
| 事务提交后事件 | 站内通知 | 事务回滚则不发通知 |
| 定时任务 | 预约 24h 未确认、订单 24h 未下单 | 每分钟扫描一次，扫描到即幂等处理 |
| 只读查询 | 商品列表、统计、操作记录 | 不加锁，走索引 |

### 4.2 三条关键交互链

**（1）预约链**：买家 → M3 预约接口 → 校验商品状态（M2 查询）→ 插入预约 → 商品转「已预约」→ 写操作记录（M5）→ 事务提交后给卖家发通知。
**（2）审核链**：卖家提交 → M2 状态转「待审核」→ 管理员审核 → 通过则「已发布」，驳回则「已驳回」+ 调 M4 记违约。
**（3）超时链**：定时任务扫到超时预约 → M3 置「已失效」、商品回「已发布」→ M4 记卖家违约 → M5 写操作记录 → 通知买家与管理员。

### 4.3 事务边界

| 操作 | 必须同一事务的内容 |
| --- | --- |
| 卖家确认预约 | 预约→已确认、商品→交易中、其余预约→已作废、订单→待下单、操作记录 |
| 下单 | 订单→已下单、操作记录 |
| 交易完成 | 订单→已完成、商品→已完成、操作记录 |
| 下架商品 | 商品→已下架、有效预约→已作废、未完成订单→已作废、通知、操作记录 |
| 审核驳回 | 商品→已驳回、违约记录 +1、操作记录 |

## 5 关键设计决策（v1）

| 编号 | 决策点 | v1 选择 | 理由 |
| --- | --- | --- | --- |
| ADR-01 | 状态机实现 | 状态模式：每个商品状态一个类 | 面向对象教材做法，新增状态时不用改已有分支 |
| ADR-02 | 唯一有效预约 | 事务内 `SELECT ... FOR UPDATE` 锁商品行后校验 | 直观，能保证同一商品串行 |
| ADR-03 | 超时处理 | `@Scheduled` 每分钟全表扫描到期记录 | 实现简单，单实例够用 |
| ADR-04 | 通知 | 业务方法内直接写通知表并同步推送 | 链路短，调试方便 |
| ADR-05 | 联系方式可见性 | 建「联系人可见性」表，状态变化时写入/回收 | 查询快，不用每次推导 |
| ADR-06 | 操作记录 | AOP 切面统一拦截写操作 | 业务代码不用关心审计 |
| ADR-07 | 逻辑删除 | 各表 `deleted` 字段 + 查询条件统一拼接 | 实现简单 |
| ADR-08 | 鉴权 | Spring Security + 会话 | 单实例不需要 JWT |

以上 8 条在人工审查后有多处调整，见《人工修改记录.md》与 v2 版本。

## 6 数据存储设计

### 6.1 表清单

| 表 | 说明 | 关键字段 |
| --- | --- | --- |
| `t_user` | 用户（买家/卖家/管理员同一张表，role 区分） | id、username（唯一）、password_hash、role、status、banned_until |
| `t_login_attempt` | 登录失败计数与锁定 | user_id、fail_count、locked_until |
| `t_product` | 商品 | id、seller_id、title、description、price、category_tag、state、version、deleted |
| `t_product_image` | 商品图片 | product_id、url、sort |
| `t_reservation` | 预约 | id、product_id、buyer_id、state、created_at、confirm_deadline、version |
| `t_order` | 订单 | id、order_no（唯一）、reservation_id、product_id、buyer_id、seller_id、state、place_deadline、version |
| `t_violation` | 违约记录 | id、user_id、type、biz_type、biz_id、occurred_at、reason |
| `t_ban` | 封禁记录 | id、user_id、start_at、end_at、reason、status |
| `t_report` | 举报 | id、reporter_id、target_type、target_id、reason、status、handled_by、handled_at |
| `t_notification` | 站内通知 | id、user_id、type、content、is_read、created_at |
| `t_operation_log` | 操作记录 | id、operator_id、action、target_type、target_id、before_state、after_state、reason、created_at |

保留策略：`t_operation_log` 保存至交易完成后 1 年，`t_report` 保存 1 年（REQ-013、REQ-027）；`t_user`、`t_order` 长期保留（REQ-017）。

### 6.2 约束与索引

- `t_user.username` 唯一索引（REQ-001）。
- `t_order.order_no` 唯一索引（REQ-025）。
- `t_reservation` 上「同一商品最多一条有效预约」的约束在 v1 由应用层加锁保证（ADR-02）。
- 商品检索组合索引：`(state, category_tag, price)`、`(state, created_at)`（REQ-022）。
- 所有列表查询默认带 `deleted = 0`。

## 7 部署设计

单机部署，与 REQ-020 的约定环境一致：

```
[用户浏览器] --HTTPS--> [Nginx :443] --静态资源--> 前端 dist
                              └--/api--> [Spring Boot :8080] --JDBC--> [MySQL 8.0 :3306]
                                              └--本地磁盘--> 商品图片目录
```

- 应用单实例，JVM 参数 `-Xmx2g`。
- 定时任务与应用在同一进程内（单实例下不会重复执行）。
- 不做集群、不做 Redis、不接 CDN，图片存本地目录，按 REQ-023 不接第三方存储。
