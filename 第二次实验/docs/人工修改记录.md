## HM-01 模块划分：5 个 → 7 个

**AI 原方案**：M1 用户与权限、M2 商品（含检索与审核）、M3 交易（含联系方式）、M4 管理（举报/违约/封禁）、M5 审计与统计。

**我看到的问题**：

1. 检索和商品写操作挤在一个模块里。REQ-022 要求 1 万条商品、20 并发下 95% 的查询 1 秒内返回，检索是纯读路径，和写路径的锁、事务完全无关，混在一起就没法单独加索引、单独优化。
2. 违约记录有两套来源：审核驳回在 M2 记一次，超时和取消在 M3 记一次，举报在 M4 再记一次。REQ-018 要求“6 个月内满 5 次封禁”，三个地方各写一遍计数，口径迟早不一致。
3. 通知没有归属模块，被写在交易模块的方法里；REQ-009、REQ-010、REQ-028 都要通知，散着写会重复三份代码。

**备选**：

- A. 拆成 7 个业务模块（检索独立、信用独立、通知独立）——采用。
- B. 只拆检索，共 6 个模块——违约口径问题没解决。
- C. 保持 5 个——改动最小，但上面的问题都留着。

**我的选择**：A。

**落地改动**：

- 新增 M3 商品检索、M5 信用与风控、M6 通知；M2 收窄为“商品写路径 + 状态机”。
- 违约记录统一由 M5 的 `CreditPort.record()` 写入，其它模块只传“谁、什么类型、关联业务 ID”。
- 连带解决两个循环依赖：商品下架要作废订单，改为 M2 发 `ProductOfflineEvent`、M4 同事务消费；审计改为 M0 定义 `AuditPort`、M7 实现，业务模块不再依赖审计模块。
- 联系方式可见性没有跟着放进“通知”模块，留在 M4。理由：它不是消息，而是由预约/订单状态推导出来的交易规则，数据归属于交易模块，放通知模块反而要多读一份交易数据。

**依据**：REQ-022（检索性能）、REQ-018（违约口径统一）、REQ-009/010/028（通知复用）、REQ-012（可见性由交易状态决定）。

## HM-02 商品状态机：状态模式 → 状态转换表 + 守卫

**AI 原方案**：抽象类 `ProductState` + 8 个状态子类，每个类实现 `submit/approve/reject/reserve/confirm/complete/offline` 等方法。

**我看到的问题**：

1. REQ-029 的验收方法是“对允许的转换逐条构造操作，对禁止的转换逐条构造操作”。状态模式下，一条转换写在哪个类里、有没有漏，只能一个个类去找；表驱动则是一张 15 行的表，可以对着需求表逐行核对。
2. 状态模式里每个状态类都要实现 7 个方法，8 个类就是 56 个空实现或抛异常的方法，真正有效的规则被淹没了。
3. 权限和封禁也在方法里判断，越权和状态非法混在一起，报错信息分不清。

**备选**：

- A. 状态转换表（from, action, to, 守卫）+ 守卫链——采用。
- B. 保留状态模式——面向对象味道足，但验收和排错都费劲。
- C. 枚举 + if 判断——写起来最快，规则和权限继续混在一起。

**我的选择**：A。

**落地改动**：

- `ProductStateMachine` 持有一张 15 条的静态转换表，`check(from, action)` 查不到就抛 `IllegalStateTransition`。
- 守卫按顺序执行：`StateGuard` → `RoleGuard` → `OwnerGuard` → `BanGuard` → `ReasonGuard`；任一失败，状态不变。
- 类图从“1 个抽象状态 + 8 个状态类”换成“状态机 + 转换规则 + 守卫接口 + 4 个守卫实现”，类少了，规则集中了。

**依据**：REQ-029（逐条验收允许/禁止转换）、REQ-002（越权拒绝）。

## HM-03 唯一有效预约：行锁 → 唯一索引 + 生成列

**AI 原方案**：事务内 `SELECT ... FOR UPDATE` 锁商品行，再查有没有有效预约，没有才插入。

**我看到的问题**：

1. 锁的是商品行本身。REQ-022 要 20 个并发查商品，同一条热门商品的详情查询会和预约事务抢同一行锁，查询被排在后面——为了一个写操作牺牲了整个读路径。
2. 正确性完全靠“每个入口都记得先加锁”。以后新加一个“管理员代预约”之类的入口，忘了加锁就出现两条有效预约，数据库拦不住。
3. 需求说的是“同一商品只允许一条有效预约”，这是一个唯一性约束，用锁去模拟唯一性约束是绕路。

**备选**：

- A. `active_key` 生成列 + 唯一索引——采用。
- B. 保留行锁——直观，但和 REQ-022 的并发目标冲突。
- C. 乐观锁 version + 失败重试——预约是插入不是更新，重试容易插两条。

**我的选择**：A。

**落地改动**：

```sql
ALTER TABLE t_reservation
  ADD COLUMN active_key BIGINT GENERATED ALWAYS AS (
    CASE WHEN state IN ('WAIT_SELLER','CONFIRMED') THEN product_id END
  ) STORED,
  ADD UNIQUE KEY uk_reservation_active (active_key);
```

- 预约插入时若同商品已有有效预约，直接抛 `DuplicateKeyException`，转成 409「该商品已被预约」；不需要先查后插。
- 预约进入终态（已取消/已失效/已作废）后 `active_key` 变 NULL，NULL 不参与唯一性，同一商品可以再次被预约。
- 行锁从预约流程里彻底去掉，商品详情查询不再和预约事务互斥。

**依据**：REQ-008（唯一有效预约、并发只有一个成功）、REQ-022（读路径不被写锁阻塞）。

## HM-04 超时与通知：全表扫描 + 同步写 → 索引分批 + 提交后推送

**AI 原方案**：`@Scheduled` 每分钟 `select * from t_reservation where confirm_deadline < now()` 全表扫；通知在业务方法里直接 insert。

**我看到的问题**：

1. `confirm_deadline` 上没索引，数据量一大就是全表扫描；而且每分钟扫一次全表，扫描本身会占连接和 IO。
2. 通知写在业务方法里，业务事务回滚了通知已经落库，用户收到一条“预约成功”但实际没成功——REQ-027 要求“操作失败时不得留下成功记录”。
3. 反过来，如果只在 `AFTER_COMMIT` 里插通知，进程在提交后、插通知前崩溃，通知就永久丢了。

**备选**：

- A. `(state, deadline)` 索引 + 每批 200 条 + 幂等 UPDATE；通知与业务同事务落库，提交后只做推送——采用。
- B. 保留 v1 写法——最短，但上面两个问题都在。
- C. MySQL EVENT 调度——业务逻辑落进数据库，调试和单测都麻烦。

**我的选择**：A。

**落地改动**：

- `idx_reservation_deadline(state, confirm_deadline)`、`idx_order_deadline(state, place_deadline)`；任务每次取 200 条，处理完继续取，直到没有到期记录。
- 每条处理都是 `UPDATE ... WHERE id = ? AND state = 'WAIT_SELLER'`，影响行数为 0 说明已被别的流程处理过，直接跳过——任务重跑也不会重复记违约。
- 通知落库放在业务事务内（与状态变更同生共死），`@TransactionalEventListener(AFTER_COMMIT)` 只负责推送未读数；推送失败只影响实时性，用户下次进消息中心仍能看到。

**依据**：REQ-010（超时自动失效、通知买家与管理员、记卖家违约）、REQ-025（订单超时）、REQ-027（失败不留成功记录）。

## HM-05 联系方式可见性：建表同步 → 实时推导

**AI 原方案**：建 `t_contact_visibility` 表，预约创建时写入、状态变化时删除，查询时读这张表。

**我看到的问题**：

1. 这张表是交易状态的一份冗余副本。预约取消、超时、作废、订单完成、订单取消、订单作废、商品下架——七条路径都要记得同步，漏一条要么泄露联系方式，要么该看却看不到。
2. 实验一 INT-02-L039 里甲方确认的是“可见性只由当前是否存在有效预约或未结束订单决定，无需额外定时任务”。建表等于给这个规则又加了一份可能过期的缓存。
3. 需求要求“立即回收”，建表方案还得额外处理回收失败的情况。

**备选**：

- A. 实时推导，不建表——采用。
- B. 保留可见性表——查询快，但同步点太多。
- C. 建表 + 定时清理——有回收时间差，不满足“立即回收”。

**我的选择**：A。

**落地改动**：

- 删除 `t_contact_visibility` 表。
- `ContactVisibilityPolicy.canView(buyerId, sellerId, productId)`：查该买家在该商品上是否存在 `WAIT_SELLER`/`CONFIRMED` 的预约，或 `WAIT_PLACE`/`PLACED` 的订单；管理员直接放行。
- 查询走 `(product_id, buyer_id, state)` 索引，一次查询即可判定，不需要写路径配合。

**依据**：REQ-012（五种情形下的可见性、立即回收、管理员始终可见）、INT-02-L039。

## HM-06 图的呈现：类图拆两张、用例图精简

**AI 原方案**：28 个类画在一张类图里（5890×2166）；用例图画了 22 个用例，被拉成 843×2658 的细长条。

**我看到的问题**：

1. 类图在 A4 上缩到看不清，评审时没人会放大看；而且领域对象和服务/设计模式混在一张图里，两种关注点互相干扰。
2. 用例图的问题不是画错，是太细。22 个用例连 `include` 线，结构反而看不出来；用例的细节应该放在用例描述表里，图上留主干。

**我的选择**：

- 类图拆成两张：`01_UML类图-领域模型`（实体、枚举、关系、关键方法）和 `02_UML类图-服务与模式`（应用服务、状态机、守卫、端口接口）。
- 用例图按角色视角拆成两张：`07_UML用例图-买家与卖家`（11 个用例）和 `08_UML用例图-管理员与系统`（7 个用例，含系统计时器）。合计 18 个用例，`include` 只保留“处理举报 → 违约与封禁管理”一条，登录关系用图下注释统一说明；细节写在报告的用例说明里。

**依据**：报告可读性；REQ-029 的规则细节放在状态表和守卫链里，不靠图表达。
